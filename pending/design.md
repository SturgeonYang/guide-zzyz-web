
# Next step for 2026 `Gemini生成，仅供参考`

## 1.User Authentication and Verification System

## 技术栈推荐

* **前端**：Vue 3 / React + Axios（网络请求） + Pinia / Redux（状态管理，用于本地存储 Token）。
* **后端**：Spring Boot (Java) / NestJS (Node.js) / Gin (Go)任选。
* **数据库**：MySQL（主存储） + Redis（缓存、验证码、Token 黑名单管理）。
* **安全与协议**：HTTPS + JWT (Access Token & Refresh Token) / Session + Bcrypt (哈希加密)。

## 实现原理（200字内简要说明）
>
> 本系统实现用户完整生命周期。**注册**时密码哈希加盐（Bcrypt）存入MySQL；**登录**成功则生成JWT返回前端用于身份鉴权；**登出**时清除前端Token，后端将当前Token记入Redis黑名单使其失效；**注销（销毁账号）**时，系统校验前置条件后对隐私数据逻辑删除、脱敏并去标识化（满足合规要求），同时作废该用户所有活跃Token，清理会话，待冷静期满后彻底完成数据闭环。

## 四大核心功能详细设计

### 1. 注册 (Registration)

* **流程说明**：
  1. 用户输入邮箱/手机号，通过滑块等防刷验证后，系统调用邮件/短信接口发送验证码（验证码在 Redis 中存储 5 分钟并设置 TTL）。
  2. 用户输入密码，前端校验密码强度。
  3. 后端校验验证码通过后，使用 Bcrypt 算法对密码进行单向哈希加密。
  4. 将加密后的密码与用户信息写入 MySQL，完成注册。

### 2. 登录 (Login)

* **流程说明**：
  1. 用户输入账号、密码。
  2. 后端查询数据库，比对哈希值（`bcrypt.compare`）。
  3. 验证通过后，后端生成双 Token：**Access Token**（短期有效，如 2 小时，用于接口鉴权）和 **Refresh Token**（长期有效，如 7 天，用于刷新 Access Token）。
  4. 将 Token 返回前端，前端存入 `localStorage` 或 `Cookie` 中。

### 3. 登出 (Logout)

* **流程说明**：
  1. 用户点击“退出登录”。
  2. **前端操作**：清除本地存储的 Access Token 和 Refresh Token，将用户重定向至登录页。
  3. **后端操作**：获取当前请求携带的 Access Token，将其存入 Redis **黑名单**中，设置生存时间为该 Token 的剩余有效时间。后续带有该 Token 的请求将被拦截器直接拒绝。

### 4. 注销 (Account Deletion / Deregistration)

* **流程说明**：
  1. **前置校验**：系统检查该账号是否满足注销条件（如：无未完成订单、无未提现余额、无未处理纠纷等）。
  2. **确认申请**：用户通过验证码二次确认后，系统将账号状态修改为 `注销中`，并记录注销时间 `deleted_at`。
  3. **强制退登**：系统立刻吊销该账号名下的所有活跃 Token，将其列入黑名单，强制所有设备退出登录。
  4. **冷静期与匿名化（15天后）**：
     * **冷静期内**：用户如重新登录，可申请撤销注销。
     * **冷静期满**：定时任务（Cron Job）执行，将该用户的敏感隐私数据（如手机、邮箱、真实姓名）进行**去标识化（脱敏/匿名化）**处理（例如：将 `张三` 改为 `deleted_user_1028`），以便保留历史订单/账单数据进行对账，同时彻底销毁用户个人隐私信息。

## 数据库核心字段设计 (MySQL)

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | bigint | 唯一主键 |
| `email` | varchar | 绑定邮箱（唯一索引，注销后可加随机后缀释放占用） |
| `password_hash` | varchar | 加密后的密码哈希值 |
| `status` | tinyint | 状态：1-正常，2-注销中，3-已注销 |
| `is_deleted` | tinyint | 是否删除：0-未删除，1-已删除（逻辑删除标记） |
| `deleted_at` | datetime | 注销/删除时间（用于冷静期计算） |

## 2.用账号发评论功能设计

## 整体设计思路

核心目标是把**账号登录态（JWT）**与我们之前做好的**树状嵌套评论（自关联表）**连接起来。

* **安全原则**：前端调用发表/回复评论接口时，**不传递 `userId`**，后端统一从 Header 的 Token 中解密提取，防止抓包篡改。
* **数据原则**：保持评论树的拓扑结构完整。

## 核心技术点与讨论议题（团队开发重点）

### 1. 身份如何绑定（Auth 拦截）

* **流程**：
  * 前端请求拦截器自动在 `Authorization` 头部带上 Token。
  * 后端 Auth 中间件校验 Token，解析出当前用户的 `userId`，然后**挂载到 `req.user`（或全局上下文）**。
  * 写入数据库时，从 `req.user.id` 获取值写入 `comments.user_id`。

### 2. 数据库怎么关联（加个外键）

评论表（`comments`）核心字段只需关联用户表和自身：

* `user_id`：关联用户表 ID（用于知道是谁发的）。
* `parent_id`：指向父评论 ID（用于构建您之前实现的树状结构，根节点设为 `null`）。

### 3. 【重点讨论】账号注销了，评论树怎么处理？

当用户在系统里注销（销毁）账号时，他的树状评论**不能物理删除**。

* **为什么**：因为是树状结构（套娃回复），如果删了 A，后面回复 A 的 B、C、D 评论会因为找不到父级（`parent_id` 悬空）导致树结构断裂报错。
* **解决方案**：采用**逻辑匿名化**。注销时，后端把该用户的 `comments` 数据的 `user_id` 改为 `0`（系统占位用户），并将内容脱敏（如改为“该用户已注销”）。这样既抹去了隐私，又保全了树的完整性。

### 4. 权限与越权控制

* **删除/修改自己发表的评论**：后端接口除了验证 Token 登录态，必须加上条件判断：`当前登录的 userId == 评论记录的 user_id`，防止他人通过拼接 API 恶意删除别人的评论。
